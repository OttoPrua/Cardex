# Cardex 本轮重构目标（Otto 2026-10-30 确认）

本文件是本轮重构的目标锁定。计划、Goal prompt 和复核只能在这里写明的范围内展开；超出部分交 Otto 拍板。

## 终态定位

Cardex 是目标驱动的自动编程管理派发器。它面向本地多渠道订阅模型，初衷是高效使用这些额度。

- 需求模糊时，持续派设计卡；设计按层逐步细化，不要求一开始定完。
- 某一层设计确认后，就在这一层下面派开发卡；设计和开发交错推进，直到目标完成。
- 优先级：高质量落地第一，省 token 第二。
- 并行：最大化并行，包括同一文件的不同模组，以及同一模组内互不干涉的部分。见第 12 条。

约束原则（针对过去“模型产出或新建的卡不合流程就整条失败或暂停”）：
- 硬底线只保留少数安全与正确性约束：写域冲突、预算硬上限、不泄露密钥、不越权 push/安装/删除、FrozenRoute、测试必须通过。只有违反这些才阻断。
- 其他流程要求一律降为软约束，包括输出格式、回执字段、卡片字段完整性、命令顺序、证据指针。不符合时由 Cardex 自动补全或修正：缺字段用默认值，写域从实际 diff 推断，格式不对就用宽松解析或一张便宜的整理卡提取结果。实在处理不了的，标记为“待复核”，不判失败。
- 按结果验收：看测试是否通过、复核是否通过、改动是否落在写域内，不看过程是否逐步合规。
- 失败就地处理：一张卡失败只影响它自己和直接依赖它的卡，先自动派修复卡；其他分支和整个目标继续推进。
- 新增约束要有理由：任何新的门禁或校验，都必须写明它防的是哪一类真实失败。说不出的不加。复核时同样适用。
- 回执和证据由 Cardex 的事件日志自动记录，不再要求执行者手工产出 SHA、读回等仪式性材料。

架构原则：
- 机械部分在 Go 里做成确定性状态机，包括派发、合并、预算和门禁。
- 判断部分本身也做成卡，路由给合适的模型，包括设计、拆卡、复核和重规划。
- 除入队分级外，Cardex 不直接调用模型。

## 目标

### 一、减法与收敛（先做）

1. **减法重构。**
   - 删除：退役的 Gemini、claudego 兼容（`.claudego`、`com.claudego.tick`、install-shim）、仓内旧二进制、事故专用恢复入口（goal-bootstrap-before-native-recovery 等）、cmd cross 及其模板、assemble/plan/brief -auto、一次性授权流程、deadcode、过期文档。
   - 保留：grok-build、codex、claude（含 engines 档案）、cursor、kimi-cli、agy、opencode 七个执行器。
   - 旧数据：通过切换时的一次性导入，在 v2 里仍能列出、查看和复核旧卡（见“落地形式”）。
   - 判定边界：属于核心编排的入口不删，列为待 Otto 拍板。
2. **路由收成一套。** 只保留 presets、work_class_routes 和 FrozenRoute 三层。删除旧 fallback_order、codex_fallback 和 legacyAutoFallback。Owner 矩阵和 mixed routing 合并进 work_class_routes。新卡行为可以变，旧卡已冻结的路线不变。

### 二、选模型

3. **按意图分级路由（参考 Magpie）。**
   - 分级方式：入队时用一个便宜模型做难度和意图分级，失败时退回规则分级。
   - 冻结：分级结果写进卡，并冻结进 FrozenRoute。
   - 优先级：管理者显式指定的 preset 或 runner 优先于自动分级。
   - 可追踪：每张卡都能查到路由理由。
4. **同层按余量排序与用量红线。**
   - 排序：同一能力层级、同一来源的候选里，优先选离刷新时间更近且仍有余量的渠道。
   - 红线：每个渠道可设用量红线（例如 opencode 保留一定额度）。低于红线不再被自动选中，只有显式指定时才用。现有三通道 redline 统一进这套机制，不删。
   - 时机：选择只发生在派发前。运行中不改道。现有“只有证明配额耗尽且零活动才回退，auth、refusal、transport、budget_limited 不改路由”的规则不变。
5. **模型定位定时任务。**
   - 形式：Cardex 内置一份固定 prompt，定期派给能联网搜索的外部 Agent。
   - 工作：查权威榜单上软件开发相关的模型排名，并结合第 11 条内部成绩单，产出“渠道 × 模型 → 能力层级和分工”的提案，以及与当前配置的差异。渠道出现新模型时提醒定位。
   - 生效：只出提案。Otto 或管理 Agent 确认后才写入路由配置。

### 三、自动闭环

6. **目标对象。**
   - 内容：每个目标带验收标准、总预算和优先级，所有卡挂在某个目标下。
   - 结束：达标、预算用完或阻塞时停止。
   - 启用：自动推进按目标开启；未开启自动的 workflow 仍走现有手动路径（advance 需 `-opt-in`）。
7. **分层设计、逐层冻结，设计与开发交错推进。** 不要求一开始定完全部设计。
   - 设计树：设计按层组织，例如目标与方向、模块划分、模块内细节。每个节点有自己的开放问题清单和状态：待设计、可冻结、已冻结、已重开。
   - 逐层冻结：某个节点冻结后，它下面就可以拆卡开发；兄弟节点和更深的层可以继续设计。
   - 冻结确认有两种模式，Otto 可在开发中随时切换：
     - 稳妥模式：目标方向和模块划分两层由 Otto 确认；模块内细节在复核卡通过后自动冻结，事后可以重开。
     - 快速模式：只有最顶层的目标方向由 Otto 确认，其余各层自动冻结。
   - 用实做验证设计：设计期可以派原型卡或试验卡，专门回答“做了才知道”的问题。结果回填到对应的开放问题，原型代码默认不直接并入主线。
   - 开发反哺设计：开发中发现的新问题挂回对应设计节点。若需要推翻已冻结的设计，重开该节点须 Otto 确认，并自动触发受影响卡的重规划。
   - 开发期：已冻结节点下的开发全自动推进，只有待拍板问题和熔断才找 Otto。
8. **拆卡卡与重规划卡。**
   - 拆卡：按已冻结的设计节点逐个生成卡片依赖图，每张卡带写域、依赖和验收测试。
   - 重规划：每轮结束自动派一张重规划卡，按实际结果调整剩下的卡。
   - 接口先行：先派骨架卡定接口和桩，其余卡在接口后面并行实现。
9. **跨模型复核与熔断。**
   - 复核：每张开发卡完成后，自动派一张由另一家模型做的复核卡，使用固定复核约束 prompt。返工超过上限就升级。
   - 熔断：连续失败、同一错误重复、测试变红、无进展时，停掉这条分支并上报。
   - 阻塞范围：待拍板问题只阻塞相关分支，其他分支照常推进。
10. **待拍板与熔断推送。** 优先推回创建该任务的会话（Hermes 或 Codex 等管理会话），目的地可配置。未回复不等于接受。

### 四、并行与成本

11. **内部成绩单。** 按“模型 × 任务类型”记录验收率、返工率，以及每张验收通过的卡花了多少 token。它作为第 4、5 条的依据之一。
12. **最大化并行（硬目标）。** 过去多次优化未完成，主因之一是锁太粗：常常整个 worktree 被锁，或者一个功能项的全部文件被锁，导致同一功能下的多个子功能无法同时开发。本轮要求：
    - 锁的单位是“卡声明要改的符号”，不再是 worktree 或功能项。worktree 只是每张卡自己的隔离工作区，不作为锁。
    - 符号级写域：写域从文件级细化到函数和类型级。Go 用语法树解析，其他语言用 tree-sitter，解析失败时退回文件级，并在路由理由里注明退回原因。
    - 声明式加乐观式：卡在派发前声明要改的符号，只对这些符号互斥。声明之外的顺带改动不预先加锁，而是在合并队列里检测；有冲突时派变基卡，而不是事前拒绝派发。
    - 只读不锁：读取、测试、复核不占写域。
    - 可验证：守护测试里加入“同一文件、同一功能下两个子功能的卡同时运行并都合并成功”的场景。看板显示当前被占的符号和等待原因。
13. **合并队列。** 每张卡在独立 worktree 里做，完成后进入串行合并队列，合并后跑全量测试。冲突或测试变红时，自动派修复卡或变基卡。
14. **稳定上下文包。** 每个目标生成一份固定前缀（项目约定、冻结设计、接口），所有卡复用同一前缀，以命中各家 prompt cache。
15. **余量填充。** 渠道临近刷新且仍有余量时，自动拉低风险积压卡（补测试、补文档、小重构）把它用掉。低于红线的渠道不动。

### 五、看板

16. **看板重做。**
    - 默认视图：只显示当前项目、未结束的卡和近期动态。
    - 历史：历史卡和历史项目默认收起，不删数据。
    - 新增展示：目标进度、设计树（各节点状态与开放问题数）、依赖图完成度、并行 lane、合并队列，以及各渠道的余量、刷新时间、红线和路由理由。
    - 看板仍然只读。

### 底线不退化

17. **以下行为保持不变：**
    - tick 排空队列；
    - 手动 workflow 的 fanout/accept/advance（`-opt-in`）；
    - Grok 原生 `/goal` 的 goal-run/goal-sync（`budget_limited` 不等于 done）；
    - admission/lease/write-domain/pause；
    - 依赖 DAG；
    - FrozenRoute 语义。

## 不做（本轮）

- 不搬 Magpie 的网关和协议翻译。
- 不改各 CLI 的家目录。
- 不做运行中遇到 429 就换 runner。
- 不删旧卡数据。
- 不做脱敏、插件和可撤销的 Agent 配置接线。
- 不做返工续用原会话（留待后续）。
- 重构期间不替换已安装的 CLI 0.10.43、board 和 launchd。安装和 Release 需 Otto 授权。

## 落地形式（Otto 2026-10-30 确认）

- 设计依据：按本文件的目标和第一性原理重新设计，不拘泥于现有程序结构和设计文件。旧代码只作参考和素材来源，例如各 CLI 的调用细节、Grok `/goal` 的 PTY 托管、错误分类。过去遇到的问题（锁太粗、流程约束太严、held 和 failed 堆积）作为设计输入。
- 不逐个组件替换：在运行环境之外完整构建 v2，避免新旧并存带来的冗余和框架问题。
- 隔离：v2 开发期间只用独立的数据目录和端口，不注册 launchd，不读写 `~/.cardex`。现在运行中的 Cardex 0.10.43 照常工作，并负责派发 v2 的开发任务。
- 一次性切换：v2 验收后，经 Otto 授权一次性替换当前运行的 CLI、board 和 launchd。切换前保留旧二进制和旧数据目录作为回退锚点。
- 旧数据：切换时一次性导入。未结束的卡导入为可继续的卡，其余导入为只读历史，看板默认收起。旧数据目录原样保留，用于回退。
- 命令界面：按新设计重新定义，不保持旧命令兼容。切换时同步重写 cardex-dispatch skill，供 Hermes、Codex 等管理会话使用。
- 第一部分“减法”的含义随之改变：v2 根本不带入这些旧件，而不是在旧代码里逐个删除。第 17 条“底线不退化”的含义是能力等价，不要求命令和参数与旧版一致。

## 顺序

1. 开工前先做两件事：
   - 历史失败调查：把 `~/.cardex` 里 held 和 failed 的卡按根因分类，例如锁冲突、准入阻塞、额度等待、认证、超时、预算用尽、人工封存，以及“产出或新卡不符合流程要求而被拒、失败或暂停”。统计每类的数量和代表卡，并标出哪些根因由本轮哪一条目标消除。没有被任何目标覆盖的根因，交 Otto 决定是否纳入。
   - 建立底线守护测试。
2. 设计 v2，并在隔离环境中构建、验证。
3. 迁移旧数据，然后在 Otto 授权下一次性切换。

守护测试改为针对 v2 的能力验收，全程保持常绿。

## 已知缺口（由计划阶段核实）

- 各渠道“剩余用量和刷新时间”的数据来源：CLI 自报、错误信息里带的重置时间、本地计量、手工配置周期，各渠道情况不同。
- 现有 manager_wake 能否作为“推回创建会话”的通道，以及 Hermes 和 Codex 会话如何识别。
- 现有 write-domain、worktree 和集成机制能细化到什么程度。
- 主 checkout 里 `attempt_control.go` 有未提交的 CAS overlay，开新 worktree 前要决定先提交还是保留。
- 删除路由旧键对现有 `~/.cardex` 配置的影响。
