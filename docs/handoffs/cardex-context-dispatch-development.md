# Cardex：程序化派发与上下文规则开发 Prompt

你是 Cardex 专门开发 Session。请按下列清单逐项实现，完成每项的代码、相关验证和必要修复后再推进下一项；不要只交方案或把规则仅写进提示词。

## 目标与基线

仓库：https://github.com/OttoPrua/Cardex 。需求讨论基线为 v0.10.22，提交 `0911971d977db5debb0d65bd7db2f5f5a2e78c08`；开始时核实当前分支和差异，在已有工作上修正，不为对齐基线重置或丢弃修改。

目标：owner 确认工作方式、可用订阅和模型偏好后，让 Cardex 程序负责后续可确定的派发、会话复用和上下文交接规则。管理 Agent 仍负责理解目标、设计规划和必要决策；不要让每次普通派发都再调用一个模型来决定规则。

存在三种用户工作方式：
1. 单卡直派：一个明确任务，指定或采用预设的 runner/model/effort。
2. 单阶段编排：一张设计卡对应多张执行卡，独立方向按依赖并行推进，最后汇总到一张验收卡。不是只支持设计、执行、验收各一张的串行链。
3. 自持开发，额外选择两种派遣方法：
   - 分阶段循环派遣：同一整体目标下，多轮组织“设计卡 → 多张执行卡 → 验收卡”，按每轮结果推进下一轮，直到目标完成或需要 owner 决策。
   - 模型原生 Goal 派遣：使用实际适配器支持的原生 `goal` 能力，每个会话持续推进分配给自己的目标。允许一个会话，也允许多个独立会话分别推进不同方向；每个会话内部连续开发、测试和普通修复，结果再汇总。不得把该方法限制为整个目标只有一个会话。

两种目标派遣方法都可以并行；区别是持续推进由管理层多轮编排，还是由各个原生 Goal 会话执行。可组合使用：循环派遣中的独立执行方向交给原生 Goal 会话。并行依据真实依赖、写入范围与资源约束，不能让多个活跃 attempt 共用一个执行 Session，也不能制造重复 writer。不是无限自治，不把每个工具调用都拆成卡。

原生 Goal 派遣必须保留目标级收口：目标所需的各个 Goal 会话开发完成、终态核实后，汇总全部方向的当前产物，统一进行一轮整体验收；验收通过前不能把总目标标为已验收。不要用每个会话的自检或一组独立完成状态替代整体验收。

当前源码核实：`goal-sync` 更新单个 writer 的阶段事实，不自动派 reviewer；`workflow review` 需要显式调用，绑定单个 writer 和冻结候选；`parent_id` 本身没有实现全部子 Goal 完成后的聚合验收。现阶段管理 Agent 可以组织收口，程序自动聚合仍需实现。复用现有 DAG/审核机制，以目标的明确成员范围等待全部必要方向；部分完成、失败、暂停或未知不能触发成功收口。幂等创建一张整体验收卡，绑定汇总候选与各方向产物；新增方向或候选变化要重新确认验收覆盖，不能沿用旧结果。

工作模式与上下文策略是两个独立维度。任务卡不等于一次模型调用，也不必天然等于一个全新 Session。服务端缓存不等于会话记忆；同 Session 不保证命中，新 Session 也不等于公共前缀全部失效。不能保证换 provider/model 后继续复用缓存。

README 已按 owner 确认的方向制作配图，自动规则仍明确标为待开发。保留文档和配图；只有实际功能通过验证后才能在对应文档中改为已实现。配图由文档会话维护，不在此次运行时开发范围内。

## 先看实际路径

优先复用现有实现，不创建第二套调度器、队列或管理状态库。检查：
- `main.go`、`presets.go`、`setup.go`：add、预设、首次配置与 inventory。
- `config.go`、`mixed_routing.go`、`routing_policy.go`：配置、现有路由、显式选择与冻结身份。
- `runner.go`、`grok.go`、`kimi.go` 和其他执行器：实际启动参数、SessionID、FreshSteps、续跑限制和结果解析。
- `workflow_goal.go`、`workflow_goal_host*.go`：阶段、设计会话、Goal、原生能力与终态。
- `attempt_control.go`、平台进程实现：准入、取消、attempt、归属和退出确认。
- `manager_wake*.go`、`cmd_digest.go`、现有 usage/日志解析：回调、摘要与可用的用量事实。
- `scripts/smoke.py`、`scripts/test-install.py`、既有 Go 测试和 `.github/workflows/validate.yml`。
- `docs/getting-started.md`、`docs/dispatch-agent.md`、`skills/cardex-dispatch/SKILL.md`：安装后同一对话引导。

先确认三种工作方式哪些已有运行机制，哪些仅是管理约定；列出每个执行器目前真正支持的 resume/fresh/Goal 行为。不要把 CLI 新版本的可能能力直接视为当前适配器已经实现。

## 1. 建立一条真实可运行的规则路径

先打通“读取已确认偏好 → 生成派发决策 → dry-run 可见 → 实际启动消费同一个决策”的最小链路。

沿现有配置/预设及 Task/Workflow 表达必要字段，名称由代码结构决定，不预造大量配置键。工作方式可按项目或目标选择；选择自持开发时额外区分“分阶段循环派遣／模型原生 Goal 派遣”，并发数量与该选择分开处理，不以会话数量推断模式。模型预设长期复用。已有卡在升级后保持原语义，旧配置无需重写。

规则优先级：已有安全/权限/冻结任务合同为硬限制；其内以 owner 明确选择优先，其次已确认的目标/项目策略，最后才是默认推荐。冲突时返回具体原因，不悄悄覆盖手调值或当前执行身份。

owner 在引导中一次确认规则后，普通后续派发不再逐卡问同样问题。超出原 provider/数据/费用授权、不可推导的业务选择才回到 owner。模式识别不确定时，管理 Agent 提出建议并澄清，不靠程序猜出完整项目规划。

## 2. 实现会话决策，不以卡 ID 决定新会话

将下面条件写成运行时决策与回归检查，不只是 skill 建议：

| 输入情况 | 必须达到的行为 |
|---|---|
| 同一有界阶段、同角色，执行身份与环境兼容，前次结果及归属允许继续，CLI 支持续跑 | 优先复用该阶段的有效执行 Session；模型调用由原适配器进行 |
| 前次已安全退出，新卡明确接续同阶段工作 | 只在已支持的适配器上绑定精确前驱身份；不得与旧会话并发运行，不任意拿最近一个 Session |
| 执行任务正常需要修改、测试、普通修复 | 尽量作为完整有界工作单元完成，不为每条命令创建新卡 |
| 独立审核 | 新审核会话，不继承作者完整推理历史；提供需求、验收标准、候选差异和必要源码入口 |
| 模型/provider/角色/目录/权限或工具配置改变 | 按实际兼容性重新判断；不能跨 provider 传递旧 SessionID，也不能为保缓存规避必要隔离 |
| CLI 不支持所需 resume | 显示不支持原因；只在既有授权及安全退出条件满足时用 fresh＋必要状态，不伪称续跑 |
| 前次仍运行、归属未知、取消或结果不明 | 保留已有恢复与禁止重复执行的行为，不因新策略自动重发、切 provider 或复活取消任务 |
| owner 显式要求 fresh 或设置了有效的兼容续跑选择 | 遵循其选择；不支持的选择明确报错，不静默改成别的行为 |

不要只检查 SessionID 非空；复用需绑定目标/阶段、角色、执行器/模型、工作目录及旧 attempt 状态等真实兼容条件。具体最小字段从现有状态提取，勿照表重复存储全部信息。

## 3. 上下文准备与阶段交接

提供一个可复用的最小任务上下文，保留目标、范围、完成标准、当前完成状态、必要源码/产物入口、阻塞和下一步。大型设计文档和旧日志用指针按需读，避免复制管理会话全文。

稳定指令与当前任务变化部分分开构造；不要把每次变化的卡号/时间戳等无必要内容放到可复用前缀最前面。必须先确认对应 CLI 实际怎样组装输入，再声称此调整影响了缓存。不能为追求缓存省略任务身份、删掉必要限制或扩展数据接收方。

阶段边界可写回现有进度/结果记录，并在允许的时机用于新上下文接续。不要在每轮调用中摘要重写整个前缀，也不要为了保缓存无限携带无关历史。

若要自动触发重建，先依赖实际可观测的上下文限制/适配器信号和明确的阶段边界；没有可信 token/context 观测时标为未知，不发明一个通用百分比阈值。先让可用路径工作，再补确有需要的参数。

任何新会话交接不能丢掉未完成工作。文件记录可以恢复任务事实，不能保证恢复模型内部状态或证明中断前的工具调用已成功。

## 4. 管理摘要与用量可见性

复用现有 digest/manager-wake：默认回传状态变化、产物/验证入口、阻塞和下一步；无变化不重复通知。不把完整模型流或所有旧历史推回主管理对话，需要细节时可以展开。

Cardex 只能管理自己发出的任务、事件与上下文包。外部 Codex/Hermes 管理会话的完整历史、自动压缩和服务端缓存不一定受它控制；明确适配器能力，不声称已控制外部应用的内部记忆。

在现有日志、卡片读回或诊断输出上展示：本次工作方式、runner/model/effort、resume/fresh 判断及简短原因、所用前驱/状态入口。dry-run 不写卡、不调用模型；实际派发不能与预览选择相矛盾，状态变化时重新检查并解释。

先收集执行器真正提供的调用数、输入/缓存读写/输出等用量；区分管理、设计、执行、审核，保留来源、窗口及缺失项。reasoning 与 output 若有包含关系不能重复相加。未知不填 0；API 等价成本不冒充订阅实扣额度。不要为补全统计读取凭据或建立全量会话采集系统。

## 5. 接入新手引导并验收

安装后的同一对话应先确认可用订阅，再根据 owner 的目标推荐工作方式及对应的模型/上下文规则；自持开发额外展示派遣方法、各方向分工与可并行范围，原生 Goal 不可用时明确说明。询问采用、调整或暂不启用。展示具体建议后才保存，已有明确采用授权不重复询问。管理会话与执行模型可以不同。

优先走现有 preset/config 导入、备份和读回。确认模式/路由不等于允许立刻运行整条队列，也不等于自动授权付费模型试跑。仅改文字不能算规则完成。

使用现有测试与本地假 CLI 覆盖：
- 同阶段续跑确实传递正确 Session，并保留上下文身份；fresh 确实不携带旧身份。
- 一张设计卡派生多张独立执行卡，验收卡等待所需前驱；同一目标多轮编排保留已完成工作，完成后不再开启下一轮。
- 原生 Goal 方法允许多个独立 Session 并行且各自连续推进；各方向身份、上下文和结果不串用，仍遵守依赖、写入范围和并发约束。
- 所需 Goal 全部完成后仅创建一张整体验收卡；部分完成、暂停、失败、未知不误触发，重复完成通知不重复创建，验收覆盖全部必要方向与当前汇总候选，验收未通过不标记总目标已验收。
- reviewer 不复用作者 Session；同时启动同 Session 被阻止。
- 模型/provider/目录不兼容、不支持 resume、旧 attempt 未退出、取消与中断场景。
- 显式选择优先、旧配置/已入队卡不被迁移、重复恢复不制造第二 writer。
- dry-run → 实际卡 → provider 参数 → 完成/异常 → 摘要读回的一条完整路径。
- 摘要默认有界、必要详情可读；用量缺失不伪造；Windows 未支持能力保持准确。

先跑改动涉及的检查，完成后按仓库要求运行必要回归；失败就修具体问题，保留已完成工作。两轮同类失败后重新判断原因，不重写整个方案或静默降低断言。此阶段不调用真实付费 provider、不发布 Release、不修改用户生产队列/订阅，除非 owner 在开发会话另外授权。

## 交付与完成标准

逐项汇报已完成的运行路径、相关检查和未支持边界。最终给出代码改动、可复现命令与实际输出摘要；明确作者自审，不冒称独立审核。用户应该能看见“一次已确认配置，后续由程序一致决策”，而非继续人工指定每张卡的上下文策略。

当前还没有充分数据证明哪种模式更省总 token；不要承诺固定节省百分比。完成可观察的最小链路后，用同类任务比较总输入、缓存、输出、管理调用和返工，再决定进一步优化。
