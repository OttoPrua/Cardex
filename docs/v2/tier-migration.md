# T1–T3 档位迁移与回滚

档位数字不是模型 ID。新版本只改使用者看到的编号，原配置使用的模型 ID、渠道、账号、偏好顺序、成本规则、卡种过滤、目标和依赖保持不变。

| 旧库 | 新库 | 同一能力 |
|---|---|---|
| T1 | T3 | 轻量：研究、整理、完成度检查 |
| T2 | T2 | 常规：开发 |
| T3 | T1 | 高强度：设计、复杂改动与高风险复核 |

例如旧已发布定位表把某个强模型列为 T3、一个轻模型列为 T1，迁移后它们分别是 T1 和 T3，原有卡仍按原配置选模型。旧版预设或手写定位表即使本来就不合预期，升级也保留**已记录的**路由映射，不会替用户重新选模型。新装 setup 已以推荐强模型为 T1、轻模型为 T3。

## 升级

1. 停止新派发，等旧程序把运行中的尝试、待收割结果和计划/设计的整理卡处理完，再停止调度器。检查所有使用同一数据目录的管理会话是否已退出旧版；不混跑两个版本。迁移会拒绝有开始时间但未结案的尝试，也会拒绝涉及档位的已退出未收割尝试，即使对应卡已暂停或取消。对于旧程序关闭后遗留的未完成记录，应先查清状态，不要手写结束时间绕过保护。
2. 保存旧二进制、数据库一致性备份及 home 配置/定位提案，在**另一个目录**验证备份能打开。使用支持 SQLite WAL 的一致性备份，或退出所有写者并检查 WAL 已 checkpoint 后复制；不要只复制活跃数据库的主文件。确认备份的 `PRAGMA integrity_check` 返回 `ok`。
3. 先在备份副本执行 `cardex --home <副本> migrate tiers --yes`。普通命令打开旧库会停止，不会自动激活。命令将 SQLite 一致性备份保存到已配置的备份目录，未配置时用 home 下的 `backups`（Windows 须先准备该目录），并记录新版 schema。对照轻量与强档卡，比较同一模型 ID、渠道和偏好；再按同样步骤切换正式目录。重复执行不会反复变更；未知数据库档位、待消化的旧计划或排名结果，以及从旧设计、计划或重规划衍生的未结束整理卡都会挡住激活。
4. 严格依赖（D1）使用 schema 13，调研成果血缘（ST1）使用 schema 14，档位激活使用 schema 15 及独立的语义凭据。已有 schema 14 及更早的数据库都需要显式激活；全新空数据库直接初始化到当前版本。
5. SQLite 的 cards、channels、positioning 和 attempts 路由证据一直保留旧的**存储编号**。新程序在读写边界转换编号；旧程序仍读到它理解的编号。原数据库和事件里的旧编号是可查的历史出处。旧版及新版收割证据文件也保留兼容编号；新版 CLI 读取摘要时显示新编号，不改历史文件。旧复核卡嵌入正文的机器档位和新版生成的机器档位都采用兼容编码，强档复核下限不会降低。

已有 `config.json` 的 `positioning` 及 `schedules[].card_template.tier` 不重写，没标记就按旧约定读入。若编辑为新档位，在同一文件一次性调整这两个区块的档位并加顶层 `"tier_convention": "t1-strongest-v1"`。旧提案原文件保留；尚未发布的旧提案用新语义重新提交，审批不会偷偷翻译一份带旧标签的 diff，旧审批也不会挡住新的有效提案。新版提案的磁盘档位沿用兼容编码，CLI 列表显示新编号。直接提交给新版 `positioning propose --file` 的档位使用新约定。

## 回滚

先停止新版调度器和管理会话，保留新版副本作为证据。恢复升级前备份到单独目录，且同时恢复旧版 home 配置与旧二进制。在副本上验证完整性、原架构版本和原模型路由，再切换入口。不要同时从两个版本运行调度器、管理命令或启用同一份 home 配置。不要用旧二进制接管新版正在工作的 home。数据库存储编号兼容不代表两个调度器可以混跑，也不代表新版生成的提示词、未收割文件、配置或其他迁移可被旧版完全理解。不要运行全局字符串替换。升级后生成的记录不能通过回滚自动保留，应单独保管并按事先约定核对。
