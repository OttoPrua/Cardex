# CardeX V2 双机升级与回滚

适用于已在用的 V2。首次安装、V1 导入另见[从 V1 升级到 V2](upgrade-from-v1.md)。本手册不会启动新任务；升级、停服务与启用真实渠道都要在已批准的维护窗口内进行。

## 1. 每台机先做只读盘点

分别记下：机器、操作系统和架构、服务实际执行的二进制、`CARDEX_HOME`、服务标识、管理会话实际使用的入口、当前版本及提交、二进制 SHA-256。比对服务指向的文件与终端找到的文件，不假定它们相同。只保存必要的路径和散列到私有记录；不要导出环境变量、渠道配置、密钥、数据库或通知内容。

| 机器 | 起点 | 只核对这些字段 |
| --- | --- | --- |
| Mac launchd | `launchctl print "gui/$(id -u)/<LABEL>"`（已确认是用户级 agent 时；系统服务用其实际域） | 服务标签、实际可执行文件、状态、PID。不要粘贴完整输出。 |
| 5090 | 先查实际 OS／架构和启动方式。Linux systemd 可用 `systemctl --user show <UNIT> -p ActiveState -p MainPID -p FragmentPath`；系统单元用其实际管理域。Windows 只在已确认是 Windows 服务时，用 `Get-Service -Name '<SERVICE_NAME>'` 并私下核对实际程序入口；若用任务计划或 WSL 则查看其实际配置。 | 启动方式未核实，或核对不了二进制和数据目录，就不要切换。 |
| 已核对的二进制 | `"<ACTIVE_BIN>" --home "<CARDEX_HOME>" version`；Mac 用 `shasum -a 256 "<ACTIVE_BIN>"`，Linux 用 `sha256sum "<ACTIVE_BIN>"`，Windows 用 `Get-FileHash -Algorithm SHA256 -LiteralPath '<ACTIVE_BIN>'`。 | 版本、Git 提交、散列。构建来源为 unknown 或 dirty 时，不把它当成一份已核对的发布件。 |

查看对应的卡／尝试状态和宿主进程。还在运行、收割、合并或未确认结束的任务都不算空闲；刚有新进程、进程与数据库记录不符或仍有别的管理会话写入，也不要切换。将真实服务启动视为解除停派，不用“启动一下看板”核对生产。不要为了过空闲检查杀任务或改卡状态。

## 2. 在隔离目录验同一候选

两台机使用同一个候选版本和同一个 Git 提交，但各用匹配本机 OS／架构的发布件，散列通常不同。比对各自的可信发布清单、归档散列、解包后二进制散列和 `version`。不拿云端 Linux 运行当作 macOS 或 5090 实机通过。

用合成目录和假执行器跑开库、读旧数据样式、CLI 与看板健康检查。需要演练迁移时，只在已授权的隔离副本上使用，并屏蔽真实渠道、通知接收者及网络；没有这些保障就只用合成库。不要运行指向生产目录的新二进制来“看看是否能读”。

## 3. 停派并备份，两台都确认再切

1. 用本机原来的服务管理方式暂停调度。确认宿主、调度器及相应 Git 写入全部结束；再次确认没有数据写入者。如果无法确认，暂停操作。
2. 为每台机建立不同的、权限受限的备份目录。一起存旧二进制、旧服务入口、必要的非密钥配置恢复说明和 SQLite 在线备份。不要将活跃 WAL 数据库直接复制一份文件或自行删除 sidecar。源数据库和备份路径必须不同，且备份文件名此前不存在。
3. 对已知数据库路径，用本机支持的 SQLite 工具执行在线 `.backup`，完成后用只读、immutable 模式检查**备份**，且仅接受单行 `ok`。下面是本地 shell 示例；填入绝对路径。存在空格时保留相应引号；路径含引号或 URI 保留字符时，用可正确转义并验证的本地工具，不拼字符串猜路径。
4. 记录备份时间、备份 DB 和旧二进制的 SHA-256，核实读取权限。备份失败、目标不支持可靠发布或完整性不是 `ok`，两台都不切。

```sh
# 示例占位符，并非可直接粘贴到实机的一次性脚本。
# 使用已确认且停止写入的源，放入新建的专用备份目录。
sqlite3 -readonly '<SOURCE_DB_ABSOLUTE>' '.backup "<NEW_BACKUP_DB_ABSOLUTE>"'
sqlite3 -readonly 'file:<NEW_BACKUP_DB_ABSOLUTE>?immutable=1' 'PRAGMA integrity_check;'
```

## 4. 两台离线验收，再解除停派

在停派期间分别把两台机的原启动入口指向新二进制，保留旧文件。重新核对**服务实际会执行的文件**、其 SHA-256、版本及提交；若修改了启动入口，重读入口再取散列。两台的合成看板、迁移和回滚验证均应已通过，再解除停派。

`cardex serve` 一启动就会运行调度，包括收割、合并、派发和通知，并没有仅启动只读看板的参数。不能在维持停派的前提下，用它验证真实看板。若必须先在真实库上验证看板，应使用经演练、覆盖两台机器所有写入和派发入口的外部保护；无此保护就不要开真实服务进行预检。

经过已授权的统一恢复点后再启动两台真实实例；这一步可能立即派发，不能把两次启动当作原子操作。随后分别核对进程、实际版本和抓取的看板状态，再切换管理会话入口并验证每个入口的 `version`。若一台启动或健康检查失败，不再推进；只用已经验证的停派方式阻止新任务，不杀在途执行。如无法停派而不影响已开始执行的任务，保护现场、停止进一步变更，按第 5 节处理。不要把一台的成功当作完成双机升级。

> 已执行的云端 Linux 合成演练：schema 11 的隔离旧库在线备份，新二进制将独立副本迁到 12，旧二进制可以从备份恢复并读回 schema 11；这三份库完整性检查均返回 `ok`。这不是 Mac 或 5090 实机验收，后续发布候选仍需按实际版本重复。

## 5. 失败与回滚

- 切换前失败：没有改变原入口或 DB 不需要恢复文件；查清原因后按原批准的运行方式恢复旧版。
- 切换后、尚无新有效写入：停止新版及其宿主；保留失败现场另作证据，不覆盖备份。按已验证的旧版兼容关系，恢复每台机自己配套的旧二进制、服务入口及数据库快照；不要拿另一台的快照顶替。恢复目标要与新版 WAL／SHM 隔离，且替换前确认全部进程已退出。重新校验恢复库并核对旧版身份和状态，再恢复调度。
- 切换后已有新写入或运行中任务：停止继续派发，保护新版数据和记录，不能直接用发布前快照回覆盖。由所有者确认如何保住新增工作、如何回迁，以及何时允许恢复。
